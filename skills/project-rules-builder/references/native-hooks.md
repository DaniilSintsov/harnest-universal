# Standalone native hooks

Применяй вместе со справкой выбранного провайдера.

## Выбор механизма

- Инструкция или предпочтение → native Markdown. Уже существующий lint/test/CI → переиспользуй его; hook нужен только для запрошенного момента запуска или блокировки.
- Запрет поддерживаемого tool call до выполнения → синхронный `PreToolUse`. Не подключай `async` к блокирующей проверке.
- Проверка результата работы → `Stop` с ограниченным циклом исправления. Это feedback, а обязательный merge/release gate остаётся в CI.
- Не добавляй `PermissionRequest` с автоматическим allow и не ослабляй sandbox/permissions ради запуска handler. Успешный PreToolUse должен оставлять штатную проверку разрешений в силе.

## Handler и регистрация

1. Найди существующую проверку и установленный runtime. Создай handler в `.claude/hooks/` или `.codex/hooks/`; для обоих провайдеров общую проверку можно переиспользовать, но input adapter и регистрацию сверяй отдельно.
2. Читай один JSON object из stdin, проверяй используемые типы. Не вставляй `tool_input`, пути или сообщения в shell-код; формируй JSON сериализатором, запускай checks точными argv без shell-интерпретации. stdout оставь для протокола, диагностику отправляй в stderr.
3. Зафиксируй корень проекта при регистрации либо разрешай его документированным способом. Session `cwd` может быть вложенным каталогом: проверка должна запускаться из нужного project root. Для non-Git проекта не вызывай `git rev-parse`; используй корректно экранированный абсолютный путь. Проверь пробелы в путях, перемещение проекта укажи как повод обновить абсолютную регистрацию.
4. Для защиты файлов нормализуй абсолютные/относительные пути, `..` и symlinks (в том числе существующего родителя нового файла). Проверь принадлежность scope после нормализации. Для move проверяй источник и назначение; для multi-file patch — все изменения до решения по всему вызову. Ошибка разбора поддерживаемого входа не должна давать разрешение.
5. Явно обозначь пределы: файловый hook не закрывает запись через shell, PowerShell, MCP или иные инструменты. Не выдавай поиск строки в shell-команде за надёжную защиту путей. Для более широкого запрета нужны отдельно проверенное покрытие и штатные permissions/sandbox.
6. Для check задай конечный timeout короче timeout handler, ограничь сохраняемый/возвращаемый output и обработай missing executable, exception, timeout и ненулевой exit. Возвращай документированный deny/block с причиной; произвольный exit 1 или аварийное завершение handler не гарантирует блокировку хостом.
7. В `Stop` сначала проверь `stop_hook_active`. При `true` не запускай новый цикл: верни `{}` с exit 0. При `false` запусти check; успех → `{}` с exit 0, сбой → `{"decision":"block","reason":"Конкретный сбой и шаг исправления"}` с exit 0. Этот предел допускает завершение после одной попытки исправления; не называй его строгим quality gate. Если нужен строгий gate, используй CI, не бесконечный Stop.
8. Сохраняй существующие настройки и чужие handlers. Сравни event/matcher/command с уже установленным своим handler, не добавляй дубликат. Не храни один и тот же Codex handler одновременно в JSON и TOML. Записывай корректный полный конфиг атомарно после проверки.

## Минимальная проверка

Используй временный каталог и безвредные fixture-файлы; не устанавливай тестовые hooks в рабочий проект. Для созданной логики оставь небольшой runnable test, запускающий handler через его реальный stdin/stdout/exit protocol. Проверяй поведение, не формулировки инструкций.

| Сценарий | Проверяемый результат |
|---|---|
| Разрешённый и запрещённый вызов | Нет решения / корректный deny; обычное разрешение хоста не обходится |
| Вне scope, относительный путь, `..`, symlink, путь с пробелами | Scope соответствует правилу, нет обхода нормализации |
| Codex patch с несколькими файлами или move | Защищённый путь блокирует весь вызов, включая назначение move |
| Невалидный JSON/тип или неизвестная форма поддерживаемого tool input | Явная ошибка с блокировкой там, где это предусмотрено контрактом |
| Stop: check pass, fail, missing executable и timeout | Успех отличим от block и evaluation failure |
| Второй Stop с `stop_hook_active: true` | Нет повторного check/feedback loop; это не свидетельство успешного check |
| Повторная установка/удаление | Нет дублей; чужой handler и другие settings сохранены |
| Запуск из вложенного cwd | Регистрация находит handler; check использует project root |

Выбирай строки по реально реализованному механизму: правило без file guard не требует тестов парсера путей. Затем проверь конфиг штатным способом провайдера и сделай безопасный **host smoke**: фактический вызов через выбранный tool, наблюдение handler, deny до изменения и неизменность защищённого файла; для Stop — один цикл feedback. Прямой запуск скрипта не доказывает загрузку хостом.

В отчёте текущего проекта укажи дату, версии CLI/хостов, ОС, ссылки на использованный контракт, выполненные команды и уровень проверки. Не записывай версии текущей машины как требования reusable-скилла. Если отсутствует CLI, требуется trust или версия не поддерживает механизм, не обходи это флагами: сохрани проверенные артефакты и назови оставшийся шаг.
